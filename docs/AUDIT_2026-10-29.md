The normal local workflow is connected and has been exercised against a real, disposable PostgreSQL 17.10 database.
**This is not a production-readiness sign-off.** The open findings below remain important even though every documented
endpoint was reached successfully.

## Open findings requiring follow-up

These are code-review findings; concurrency exploits and every failure scenario have not been load-tested. They remain
open rather than being covered up by a passing happy-path test.

- **[P1] OTP verification is not atomic.** Challenge lookup, attempts and consumption are separate saves outside the
  user transaction. Concurrent verification can replay a valid challenge or lose attempt increments. Use an atomic
  conditional update or a row lock, with concurrent real-database tests.
  [auth.service.ts](/home/azhar/Documents/time-bank/apps/api/src/auth/auth.service.ts:164)

- **[P1] Request creation/quota/cancellation/rescheduling can partially commit.** Request save, matching, assignment
  changes, history and audit writes are separate operations. Failure can return HTTP 500 after saving business state;
  concurrent quota checks/idempotency requests can race. Make the state transitions transactional and use a durable
  outbox for matching/notifications.
  [requests.service.ts](/home/azhar/Documents/time-bank/apps/api/src/requests/requests.service.ts:235)

- **[P1] Beneficiary reads are scoped to municipality, not relationship.** Eligibility and caregiver-list endpoints
  accept any approved member in the same municipality. They do not check that the caller is the beneficiary, an
  authorized caregiver, or a coordinator/admin. Add relationship-level authorization before exposing these records.
  [beneficiaries.controller.ts](/home/azhar/Documents/time-bank/apps/api/src/beneficiaries/beneficiaries.controller.ts:52)

- **[P1] Volunteer acceptance/manual dispatch need stronger eligibility checks.** Manual dispatch verifies approved
  membership but does not require an active volunteer role, skills, unrestricted account, or a different beneficiary
  identity. Acceptance does not recheck schedule conflicts across different requests after offers were sent. Lock by
  volunteer identity and revalidate eligibility/overlap inside the acceptance transaction.
  [matching.service.ts](/home/azhar/Documents/time-bank/apps/api/src/matching/matching.service.ts:969)

- **[P1] Cross-organization offers are not discoverable/acceptable end to end.** Matching can choose a membership from
  another organization, while offers are stored under the requesting organization. Discovery and action endpoints derive
  membership from that target organization. A volunteer with only the source membership cannot reach the offer.
  Implement an explicit cross-organization authorization/discovery contract before enabling this setting.
  [matching.service.ts](/home/azhar/Documents/time-bank/apps/api/src/matching/matching.service.ts:487)

- **[P1] Automatic matching progression has no background driver.** Expiry/progression methods exist, but only
  controller calls drive them; no scheduler/worker invokes them automatically. Requests can stall until an administrator
  manually evaluates progression. Rescheduling also leaves old matching-round expiry/tier state in place.
  [matching.service.ts](/home/azhar/Documents/time-bank/apps/api/src/matching/matching.service.ts:1086)

- **[P1] Production deployment is incomplete.** The workflow uses the development compose file instead of versioned
  production image definitions, invokes a nonexistent dist/database/migrations/run.js, assumes backup shell variables
  are exported, pulls main independently of the built ref, and still has a rollback TODO. Correcting the build does not
  make this deployment safe or functional.
  [deploy.yml](/home/azhar/Documents/time-bank/.github/workflows/deploy.yml:135)

- **[P1] Real SMS provider is not implemented.** Production login is intentionally blocked with a clear 503 after this
  audit rather than pretending an SMS was delivered. A real provider, delivery-failure handling and resend/cooldown
  behavior must be implemented before launch.
  [sms.service.ts](/home/azhar/Documents/time-bank/apps/api/src/auth/sms/sms.service.ts:20)

- **[P2] Membership approval numbering and writes can race.** Numbers use approved-count + 1; concurrent approvals can
  duplicate numbers, and membership/role/approval/audit writes can partially succeed. Long organization codes can also
  exceed the 50-character membership-number column. Use a transactional sequence and bounded formatting.
  [memberships.service.ts](/home/azhar/Documents/time-bank/apps/api/src/memberships/memberships.service.ts:176)

- **[P2] Request numbers have a small collision space.** Only 90,000 random suffixes exist per organization/month; a
  collision becomes a database error. A 50-character organization code also overflows the 50-character request-number
  column. Use a bounded identifier with adequate uniqueness or a transactional sequence.
  [requests.service.ts](/home/azhar/Documents/time-bank/apps/api/src/requests/requests.service.ts:606)

- **[P2] Pre-provisioned administrators can lack identity/wallet records.** Organization onboarding can create a User
  without VerifiedIdentity or UniversalTimeWallet. OTP onboarding creates these only for brand-new users, so that
  administrator can remain without those records. Provision all three atomically or repair missing records at sign-in.
  [organizations.service.ts](/home/azhar/Documents/time-bank/apps/api/src/organizations/organizations.service.ts:86)

- **[P2] Public organization listing includes administrative records.** The public list calls findAll(true), exposing
  non-active organizations and app-build records despite the public-summary comment. Separate public summaries from
  authenticated administrative listing.
  [organizations.controller.ts](/home/azhar/Documents/time-bank/apps/api/src/organizations/organizations.controller.ts:56)

- **[P2] Monthly quotas depend on server timezone.** Month boundaries use the host’s local time. A UTC container and an
  India-local development machine can enforce different monthly quotas around midnight. Define and test the business
  timezone explicitly.
  [beneficiaries.service.ts](/home/azhar/Documents/time-bank/apps/api/src/beneficiaries/beneficiaries.service.ts:152)

- **[P2] Some malformed query values can become database errors.** Several query parameters are passed directly as
  strings instead of validated UUID/enum DTO fields. Add validation so bad category/user IDs produce a useful HTTP 400
  instead of a PostgreSQL error.
  [catalogue.controller.ts](/home/azhar/Documents/time-bank/apps/api/src/catalogue/catalogue.controller.ts:113)

## Feature and validation limits

- File/binary upload, service timers/completion, ledger history, merchant redemption and emergency-alert APIs do not
  exist yet. Document submission records a storage reference only. The live app cannot fully implement those features
  until backend endpoints exist.
- Flutter tokens are intentionally in memory: restarting the app requires signing in again. Offline demo mode is
  separate from live member mode; it does not prove live synchronization.
- No real SMS delivery, public HTTPS hosting, device Wi-Fi connectivity or external provider was verified.
- Docker is not installed on this machine. Dockerfile fixes were inspected and the native builds passed; actual image
  builds need CI/Docker verification.
- Repository-wide formatting has pre-existing failures (including files in the independent mobile checkout). Changed
  code was formatted; a full formatting cleanup is separate work.
- Security-sensitive authorization changes in this working tree still need the project's human security review before
  production adoption. No production migration or deployment was performed.
- Flutter changes are in the independent repository at `/home/azhar/Documents/time-bank/apps/mobile/time_bank`; they
  must be reviewed/committed separately from the parent repository.
