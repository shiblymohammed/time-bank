# Workflow and reliability audit — 2 November 2026

Reviewed backend authentication, authorization/request creation, booking/completion, credit transfers, dashboard session
handling and Flutter session/form flows. This is a scoped code and regression audit, not a guarantee that every possible
defect has been eliminated. The previous design/spacing checks remain documented separately.

## Confirmed and fixed

| Severity | Trigger and previous effect                                                                                                                                                | Fix and evidence                                                                                                                                                                                                                                                                                                                  |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| High     | Concurrent valid OTP verification could read the same unconsumed challenge and create two sessions. Concurrent wrong guesses could overwrite one another's attempt counts. | PostgreSQL transaction and per-phone advisory lock serialize verification; the challenge row is also locked. Wrong guesses commit their attempt before returning an error. A failing concurrency unit test reproduced two sessions before the fix; real PostgreSQL tests now prove one session and a shared three-attempt budget. |
| High     | Verification filtered out consumed/expired challenges, allowing an older unconsumed code to become usable again after the newer code was consumed or expired.              | Verification checks only the latest challenge for that phone, then rejects its consumed, expired or exhausted state. PostgreSQL tests retain an older unconsumed challenge and verify that it cannot be revived.                                                                                                                  |
| Medium   | Simultaneous OTP requests could both pass the cooldown check before either inserted a challenge. Consuming a code also removed it from the cooldown query.                 | Issuance uses the same per-phone advisory lock, including when no challenge row exists. Cooldown counts the latest issuance regardless of consumption. Six concurrent requests now issue one challenge and one SMS call; the others receive 429.                                                                                  |
| High     | A delayed successful Flutter response could overwrite the next session's profile; a delayed old 401 could clear the newer session.                                         | The client rejects responses and handled transport failures whose session generation is obsolete. The store ignores this cancellation without replacing the current profile or error state. Regression tests reproduced both failures before the fix and now preserve the new profile, organization and session.                  |
| Medium   | Clearing optional preferred wards omitted the form value, then interpolation converted it to the string `null`, submitting `["null"]` as the ward list.                    | Missing input is normalized to an empty string and submitted as an empty list. The actual availability-edit widget regression clears the field and inspects the API payload.                                                                                                                                                      |

No database migration or API response-shape change is required. Only the newest OTP may be verified, and the 60-second
issuance cooldown also applies after a code was successfully used. These are deliberate corrections to the existing
single-use and cooldown rules.

## Remaining risks and release gaps

**Later follow-up:** request-creation recovery and unsafe default mock OTP are now fixed; see
[the full application audit](FULL_APPLICATION_AUDIT_2026-11-02.md) for the current list. The following records the
earlier review state.

These are distinct from the fixed regressions above:

1. **Legacy server-OTP sign-in blocker:** `SmsService` still has no production gateway. Android now uses Firebase
   instead; see [Firebase setup](FIREBASE_PHONE_AUTH.md) for deployment and real-device validation still required. The
   dashboard legacy path remains affected.
2. **Request creation recovery:** `RequestsService.createRequest` saves the request before awaiting matching and its
   audit event. Those steps are not one transaction. A later failure can return an error after the request exists, and
   idempotent retry returns the existing request before dispatching again. Transactional/outbox-based recovery is still
   required. This finding is based on service ordering; this audit did not add failure-injection tests or modify that
   path.
3. **Matching progression:** initial matching is implemented; no recurring worker advances expired offer rounds.
   Coordinator progression/dispatch remains necessary.
4. **Authentication post-commit recovery:** OTP dispatch/audit, account provisioning, session creation and login audit
   do not form one recoverable operation. Failures after a code is consumed can require a fresh code after the cooldown;
   the new lock prevents replay but does not make all sign-in side effects atomic.
5. **Mobile operational limits:** sessions remain in memory, so restarting requires sign-in. A timeout after a mutation
   can still mean the server committed it. Request and gift retry keys protect retries within the same form; reopening a
   new form creates a new operation key. Refresh existing records before repeating an uncertain operation. No offline
   queue or binary document upload is implemented.

## Validation

- Backend unit/security/router suite: **460 passed** across 35 suites.
- Real PostgreSQL concurrency/workflow suite: **59 passed**, including five new OTP concurrency/expiry tests and the
  existing permission, booking, completion, ledger, donation and membership tests.
- Dashboard tests: **20 passed**.
- Flutter suite: **56 passed**, including two new stale-session regressions and the extended availability edit
  regression.
- API TypeScript check and focused ESLint checks passed; Flutter analysis is clean.
- API and Flutter debug APK builds passed.

PostgreSQL 18 was unpacked into a temporary directory and run on loopback port 55437 with a dedicated
`ktb_matching_test_bug_audit` database. No configured development or production database was used. The disposable server
was stopped after validation. The concurrency test command requires a disposable `MATCHING_TEST_DATABASE_URL`:

```bash
pnpm --filter @ktb/api exec jest --runInBand
pnpm --filter @ktb/api test:matching:integration
pnpm --filter @ktb/web test
cd apps/mobile/time_bank
flutter analyze --no-pub
flutter test --no-pub
flutter build apk --debug --no-pub
```

No production deployment, real SMS delivery or connected physical-device test was performed. The Flutter repository is
separate from the backend repository.
